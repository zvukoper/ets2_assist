### ⭐ `1.0.38.64` — КОРЕНЬ ВСЕХ БАГОВ: локале-зависимый парсинг чисел

`LoadStaticCities` не тронут: там координаты — СТРОКИ с точкой.

⛔ **Правило:** никогда не парсить числовые `JValue` через `ToString()` + `TryParse`.

# 5. УРОКИ И ⛔ ПРАВИЛА (СВОДКА)

## 5.1 Методология диагностики

1. ⛔ **Измерять, а не догадываться.** «Замирания каждые 7–8 с» → интервалы `[AR] tick alive`;
   «проблема частоты вебсокета» → проба `ClientWebSocket` (35.3 Гц) и метки `ar_telemetry` (~28 Гц).
2. ⛔ **Проверять параметр на НЕСКОЛЬКИХ кадрах.** Если «лучшее» значение плавает — МОДЕЛЬ неверна,
   а не данных мало (доля компенсации крена: 0.78 / 1.20 / 0.00 / 0.00 — единого коэффициента НЕТ).
3. ⛔ **НЕ выводить физику из ОДНОГО кадра** и не «доказывать» знак логикой.
4. ⛔ **Строить ВТОРУЮ, НЕЗАВИСИМУЮ реализацию величины** (горизонт полотна из реальной плоскости;
   фит плоскости как проверка знака крена) — тогда правильный режим становится наблюдаемым.
5. ⛔ **Сначала проверить модель численно, потом менять знак** — «логично выглядящая» инверсия
   была бы РЕГРЕССОМ (случай индикатора ролла).
6. ⛔ **Критерий должен быть САМОСОГЛАСОВАННЫМ:** обе линии рисовать ОДНИМ базисом
   (сравнение с базисом «без крена» дало ложный результат).
7. **Метод поиска «залипаний»:** брать интервалы периодических лог-строк, сопоставлять с таймерами,
   затем искать дорогие системные вызовы в горячих путях.
8. **Метод проверки гипотез по 3 точкам:** МНК по модели с ДВУМЯ неизвестными при ТРЁХ уравнениях ⇒
   гипотеза ПРОВЕРЯЕМА, а не подгоняема (вертикальный FOV: fv=1965 px, RMS 41 px против 158 px).
9. ⛔ **Не доверять выводам, сделанным на паузе** (REST/placement).
10. **Инструментировать, а не гадать по скриншотам:** `[AR] TILT` + `[AR] HORIZON-GEOM` вскрыли
    корень за один кадр (центр уехал в −353 px — не тонкая ошибка).

   перенесён многократно, помечен «НЕ ПОТЕРЯТЬ». План: клиппинг в `BuildRoadsPath` + try/catch вокруг `DrawPath`.
4. **Расшифровка `properties.roadType.String`** в `roads.geojson` (пример `"balt11"`) → свой цвет/
   толщина/пунктир/иконка по типу (highway/local/urban). **Не начато.**
5. **Hit-test POI в `OnMouseClick` редактора** — сейчас клик по POI даёт координаты под курсором.
6. **Флапинг WS миникарты при старте** (коннект/дисконнект, рестарт анимации, точки не видны до `map_ready`)
   — не решён; возможно убрать `showUIWithAnimation` на каждый `map_ready`.
7. **Тема приложения не сохраняется** между запусками (`AppSettings`).
8. **Топливо на гибриде:** показ литров внедрён (вариант «а»); вариант «десятые доли %» не сделан.
9. **OllamaLimits.exe не проверен** реальным логином и живыми данными usage; исходники отсутствуют.
10. **Пробелы в истории:** сессии 19–34 (v1.0.38.35–.52) и версии v1.0.40.22/.23 отсутствуют в WORKLOG.

- **Кафе «У Дороги»** — большая фича: точки у перекрёстков, меню, ценность A-B-C-D, инвентарь, `quest_items.json`.

# 10. ВЫВОДЫ

1. **Главный технический инсайт проекта — локале-зависимый парсинг чисел (`1.0.38.64`).**
   Одна строка `JValue.ToString()` + `TryParse(InvariantCulture)` породила МЕСЯЦЫ ложных диагнозов:
   «масштаб ×100/×1e11», «мусорные кадры», «произвольное вращение», «парадокс ×100 POI»
   и, как следствие, реликтовые константы `1e9/1e11/1e14`. Правило `Value<double>()` стало
   машинным и применено во всех числовых путях.
2. **Второй системный класс багов — гонки состояний и таймеры.**
   `System.Windows.Forms.Timer` внутри `async`-метода не тикал ДВАЖДЫ (MapEditor2, AR-тик);
   флаг «запрос» перетирался флагом «изменилось»; JS-гонка `map_ready`→ответ за 28 мс ломала миникарту.
   Общее правило: жизненный признак логировать явно (`tick alive`), а не выяснять косвенно.
3. **Третий класс — геометрия AR: «правило пары линий» и запрет выводов по одному кадру.**
   Одиночный горизонт не различал режимы крена; решение найдено построением НЕЗАВИСИМОГО эталона
   (горизонт полотна) и численной проверкой знаков фитом нормали (16/16).
4. **Четвёртый класс — «дорогой код в горячем пути».**
   Чтение файлов в компараторе сортировки, `Process.GetProcessesByName` в кадровом коде,
   парсинг 1.9 МБ JSON на UI-потоке, ~98k фич при каждой перерисовке. Метод поиска — измерение
   интервалов периодических лог-строк и сопоставление с таймерами.
5. **Пятый класс — «удалённый механизм сглаживания` (v1.0.40.44).**
   Экстраполяция камеры была снесена в v40.30 и жалоба «14 fps» вернулась ВТОРОЙ раз.
   Итог: сглаживание подачи — обязательная часть конвейера AR, а не оптимизация.
6. **Открытый, честно зафиксированный пробел — компенсация крена камеры.**
   Модель единой «доли» неполна на реальных кадрах; следующий шаг определён (крен из `head.offset[5]`),
   но требует подтверждения на живых данных, а не подгонки. Значения заморожены (режим 2, доля 0.5).
7. **Процессная дисциплина:** разделение логов (workflow = шаги, app_data = значения),
   проверка `$LASTEXITCODE` перед разрушающей пост-обработкой, `node --check` для JS,
   сверка `exe == build.txt == manifest`, финальная сборка только через `compile.ps1`.
8. **Гигиена памяти:** 25 % WORKLOG было дубликатом (48 копий одного блока). При ведении лога
   не допускать повторной записи одного и того же блока; уникальные факты — в один раздел.
