schema: ets2-assist-architecture/v2
purpose: WinForms-приложение для ETS2: telemetry, minimap, hybrid dashboard, запись/проигрывание треков, случайные цели.

## Runtime

## Processes and ports
telemetry: game/plugin -> WebSocket/REST `localhost:8080`; API includes `/api/ws/delta/flat/?throttle=16` (AR tick is 16 ms) and `/api/rest/single/frame/paused`.
web_static: Python/overlay HTTP server `localhost:8082`; serves `data/`.
app_http: GUI HttpListener `localhost:8083`; CORS enabled.
app_ws: GUI WebSocketSharp `localhost:8084`; commands + track upload.
legacy: `Ets2Telemetry.exe` is disabled; `ets2-telemetry-server.dll` is not required by the current startup path.

## Data flow
map: `web_pda_map.html` -> telemetry 8080; commands/save 8084; trigger/targets 8083; static assets 8082.
hybrid: `web_ui_hybrid.html` -> telemetry 8080; commands 8084; `web_data.json` via static server.
telemetry_state: map uses `data/js/state.js`; hybrid uses `data/js/hybrid_ui_state.js`; both must update fuel/headOffset on every snapshot/delta.

targets_write: `POST http://localhost:8083/update_targets` with JSON array; server wraps `{customTargets:[...]}`.
ui_visibility: GUI checks pause/focus every 500 ms; sends `show_ui_first`, `show_ui`, `hide_ui` over 8084.

## Track save contract
request: client sends `{format:"compact_v2", data, meta, mapData, customTargets, requestId}` to 8084.
commands: `save_trail`, `start_recording`, `stop_recording`, `reset_recording_origin`, `add_random_target`, `remove_random_target`, `reset_target_reached`, `show_ui_first`, `show_ui`, `hide_ui`, `play_sound`.
guards: save only after actual ETS2 pause confirmation; duplicate `requestId` must not create a second track.
response: `{status:"ok"|"error", message, requestId}`.
compact: first line metadata JSON; trail `<t>;<x>;<z>;<heading>;<speed>`; data `D;...;<headOffset>`; events `E;...`.
headOffset: six numbers; index 3 is normalized heading 0..1.

camera: REAL SCS 6DoF pose (`AR/ScsCameraPose.cs`), NOT heuristics: `head_cabin = head.position + head.offset.position` -> `head_vehicle = cabin.position + cabin.offset.position + rotate(cabin.offset.orientation, head_cabin)` -> `head_world = truck.world.position + rotate(truck.world.orientation, head_vehicle)`; same hierarchy for orientation. `ScsCameraPose.Rotate` = Roll(Z) -> Pitch(X) -> Heading(Y); angles are TURN FRACTIONS (x2pi). Base head looks along local -Z (SCS: X right, Y up, Z back). Basis Forward/Right/Up is Gram-Schmidt orthonormalized in `TryCreate`. `ArGameState.CamX/Y/Z` = EYE world position; `CameraForward/Right/Up` + `CameraPoseValid`; `Yaw*/Pitch*` are DIAGNOSTICS ONLY and never used in projection. FORBIDDEN in AR runtime: EyeHeight, PitchCompensation, separate roll hack, `u` mirroring, screen smoothing, prediction, nearest-city height, wheel-plane camera height.
camera_roll_modes: CAMERA ROLL IS A MODE **AND A FRACTION**, NOT A GUESS. `_arCameraRollMode` (0 = roll 0 / game-stabilized, 1 = `-roll`, 2 = `+roll`; default **1**) plus `_arCameraRollFactor` (0..1.5, default **0.7**) = the SHARE of truck roll that reaches the camera. `Ctrl+Shift+Y` cycles the mode; `Ctrl+Shift+J`/`Ctrl+Shift+K` nudge the fraction by 0.1. The road plane always takes `_arRoll * _arTruckRollSign`.
camera_roll_reference: THE REFERENCE FOR THE CORRECT ROLL IS THE CHASSIS X AXIS. The user observed that the angle between the blue horizon and the REAL horizon equals the angle between the blue horizon and the chassis X axis — i.e. the real horizon is PARALLEL to the chassis X axis, which is already drawn in AR1. Measured frame: chassis X = -5.99 deg on screen; fraction 0.7 (mode 1) put the world horizon at -6.04 deg (0.06 deg error) at truck roll +9.56 deg, while 1.0 gave -8.64 deg. So the camera receives ~70% of the body roll.
camera_roll_model_incomplete: THE MODEL IS KNOWN TO BE INCOMPLETE — 0.7 IS NOT A CONSTANT. Checking the reference on SEVERAL frames (self-consistently: horizon and X axis rendered with the SAME basis) shows no single fraction fits: roll 9.19 -> 0.78 (residual 6.70 deg); 9.56 -> 1.20 (3.08 deg); 16 -> 0.00 (11.97 deg); -12 -> 0.00 (8.92 deg). The residual cannot be removed by scaling, so uniform roll scaling is the WRONG model. Hypothesis for future work: the ETS2 compensation acts on the camera's UP VECTOR (the head levels to a local vertical) rather than scaling the angle. RULES LEARNED: (a) verify any fitted parameter on SEVERAL independent frames — if the best value drifts per frame, the MODEL is wrong, not the data; (b) the criterion must be SELF-CONSISTENT — render both lines with the SAME camera basis (comparing against a no-roll basis gives a false result).
rear_projection: `drawRearProjection` in `data/web_heights.html` (panel in the LOWER part of the heights window): two wheels as RED RECTANGLES one wheel-diameter tall at the real track spacing; the ground line TILTS with roll together with the wheels on it; the camera point plus TWO camera axes (F white, U violet); a BLUE HORIZON above the ground plane that does NOT move with roll. Payload fields: `halfTrackM`, `wheelDiameterM`, `cameraLateralM`, `cameraHeightAboveGroundM`, `camAxisForward`/`camAxisUp` (pairs [lateral, vertical]), `cameraRollDeg`. REASON: the side view did NOT show roll, and roll is the very source of the problem.
plane_horizon_reference: THE OBJECTIVE CRITERION FOR THE CORRECT ROLL MODE. `drawPlaneHorizon` (`data/js/ar_hud.js`) draws the horizon of the REAL ROAD PLANE in WHITE (label "горизонт полотна"); the camera-basis horizon is BLUE (label "ГОРИЗОНТ МИРА"). The two are INDEPENDENT sources, so agreement is objective verification rather than guesswork. On flat road they coincide EXACTLY (verified: `[540.0,540.0]`); on a slope/roll they diverge exactly as much as the compensation is wrong. Geometry: a plane point goes to infinity along the plane's directions, so the screen position is the LIMIT of the projection = the projection of the DIRECTION (not a point), and the line is drawn through two such directions. NOTE: all three roll modes give the SAME height error (~±105 px) against the plane horizon and differ only in SLOPE (0 deg vs +6 deg) — so one horizon line is NOT enough, the PAIR is required.
plane_vs_camera_roll: THE CAMERA and the ROAD PLANE do not necessarily share the same roll handling — they are separate inputs (`ArCameraRollTurn(_arRoll)` vs `_arRoll * _arTruckRollSign`). Do not assume one value for both places without evidence.
ar_tilt_diagnostics: `LogArTiltDiagnostics` prints `[AR] TILT` (body / head / cabin / resulting camera basis: tilt, roll, `fwd.Y`, `right.Y`, `up.Y`) and `[AR] HORIZON-GEOM` (the page's own formula: `y(left/centre/right)` + line slope). USE THIS METHOD for any geometry complaint — instrument all four angle sources AND the rendered geometry instead of fitting formulas to screenshots.
projection: ONE path world->screen: `world - camera.position` -> dots with CameraForward/Right/Up -> pinhole. **TWO focal lengths**: `fh = (W/2)/tan(hFov/2)`, `fv = (H/2)/tan(vFov/2)`. `AR/CabinArProjection.Project` + `ar_hud.js projectPoint` both implement exactly this; no post-projection add-ons.
vertical_fov: `ArBridge.FovDegreesAr1Vertical` is an INDEPENDENT setting (NOT derived from the horizontal FOV). Default **64.5deg** (`AppSettings.Ar1FovVerticalDeg`, range 10..150), step **0.2deg** via `Ctrl+Shift+PGUP/PGDN`, and the value IS PERSISTED (it used to be lost on restart, forcing recalibration every time). Deriving it from the horizontal FOV through the aspect ratio is REMOVED: it produced ~59.6deg at hFov 91deg and silently moved when the horizontal FOV changed, destroying the calibration. Changing the horizontal FOV MUST NOT change the vertical one. NEVER reuse one focal for X and Y: ETS2 scales vertical and horizontal independently (config.cfg has separate `r_multimon_fov_vertical`/`r_multimon_fov_horizontal`), so a shared focal gives `dv = df*tan(tilt)` — zero at the horizon and growing with tilt. Historical measurement (kept for the method): from three screenshots, fitting `v = cy + fv*tan(b + h)` with TWO unknowns against THREE equations gave `fv = 1965 px`; a shared focal gave RMS 158 px and does not explain the data. `CabinArProjection.CabinFovDegreesVertical` <= 1 keeps the legacy single-focal path.
ar_payload: `ar_telemetry` carries the finished pose `camera{position,forward,right,up,fovDeg,valid}`, the road plane `groundPlane{valid,origin,normal,axisU,axisV,averageWheelHeight,referenceHeight,maxResidual,usedWheelCount,wheels[]}` and `heights{...}` for the heights window; legacy `placement`/`head` are status/diagnostics only. `PublishArV2Snapshot` publishes only when `_arCameraPoseValid`.
ground_plane: ROAD PLANE FROM WHEEL TELEMETRY (`AR/ArGroundPlane.cs`): `truck.wheel.position` ([[x,y,z],...], LOCAL) + `radius[]` + `on_ground[]` + `suspension.deflection[]` (+ `truck.wheels.count`; WS deltas may use indexed `truck.wheel.position.N`). Iterative solve: wheel position -> world via `ScsCameraPose.Rotate`; contact = center - Up*radius; fit `Y = aX + bZ + c`; normal `(-a,1,-b)`; contact = center - NORMAL*radius; 6 iterations; final fit + residuals. `|Ny| < 0.30` rejected. Wheels with `on_ground=false` stay in `Wheels` but do not participate in the fit. Fit runs in the TRUCK-RELATIVE frame (float precision). `suspension.deflection` is subtracted from local wheel centre Y. Exposes `HeightAt`/`IntersectRay`/`SignedDistance`/`ProjectToGridCoordinates`/`FromGrid`/`SnapToPlane`.
plane_always_horizontal: v1.0.40.37 REVERSED the earlier "build the grid on the wheel plane" decision. The user's intent for the grid is to place a point in SENSIBLE WORLD COORDINATES from ANY truck/camera attitude, so the PLANE AND GRID ARE ALWAYS PARALLEL TO THE WORLD HORIZON. A measured wheel plane diverges from the horizon by exactly the truck roll (~12 deg in the reference frame) and therefore made point placement wrong. `ArGroundPlane.CreateHorizontal(measured)` builds the visualisation plane: normal `(0,1,0)`, axes = world X/Z, height = `AverageWheelHeight` of the wheel contacts, `c` chosen so `HeightAt` returns a CONSTANT height; flag `IsHorizontal`. The measured (tilted) plane is kept in `_arMeasuredGroundPlane` — the heights window takes pitch/roll from IT (otherwise they would always read zero), and `Ctrl+Shift+U` switches "by horizon" <-> "by wheels".
truck_roll_sign: `_arTruckRollSign = +1` (was -1 — WRONG). VERIFIED INDEPENDENTLY by the PLANE FIT: with the truck rolled on flat ground the correct sign must yield a VERTICAL normal. `+1` -> normal tilt 0.00 deg (correct); `-1` -> 18.37 deg (wrong). The log showed a 9.03 deg normal tilt at a 9.187 deg truck roll — exactly the sign error. This check needs no screen and no fitting.
chassis_axes: ORIENTATION OF THE TRUCK IS SHOWN SEPARATELY (`drawChassisAxes`, `groundPlane.chassisForward/chassisRight/chassisUp` computed from the BODY orientation, not the camera): three lines through the screen centre parallel to the CHASSIS axes (local X/Z), NOT to the screen edges — X (red), Z (green), body Y (blue). Rationale: the camera compensates for tilt, so the truck's roll/pitch is invisible in the camera basis and only these axes reveal it.
ground_grid: AR1 grid and `ArRenderer.DrawPlaneGrid` are a PLAIN UNBOUNDED PLANE on `GroundPlane` (no circle, no chessboard, no effects — user decision v1.0.40.33).
