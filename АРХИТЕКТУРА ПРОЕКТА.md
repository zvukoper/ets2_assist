## Processes and ports
telemetry: game/plugin -> WebSocket/REST `localhost:8080`; API includes `/api/ws/delta/flat/?throttle=16` (AR tick is 16 ms) and `/api/rest/single/frame/paused`.
web_static: Python/overlay HTTP server `localhost:8082`; serves `data/`.
app_http: GUI HttpListener `localhost:8083`; CORS enabled.
app_ws: GUI WebSocketSharp `localhost:8084`; commands + track upload.
app_control: GUI HttpListener `localhost:8086`, ON BY DEFAULT — see external_control. Starts the SAME `StartSystemAsync()` as the Start button, so overlays can be raised without a mouse (test scripts).
external_control: `AppSettings.ExternalControlEnabled` (default `true`; a settings file written by an older version is migrated once via `ExternalControlDefaultApplied`, because that version always wrote `false` as its own default) + `AppSettings.ExternalControlPort` (default 8086, valid 1024..65535). Routes: `GET|POST /start`, `/start?force=1` (restarts overlays when already running), `/stop`, `/restart_overlay`, `GET /status` (JSON: running, overlayWindows, overlayProcess, game, paused, externalControlPort, version). The listener is created in the MainForm constructor — BEFORE the system starts — and deliberately NOT stopped by `StopSystem()`, otherwise `/start` would work only once per session. Every request logs `[CONTROL] …`.
external_control_cli: `ETS2_Assist.exe --start` raises the system without a mouse: a running instance receives the `Local\ETS2_Assist_StartSignal` EventWaitHandle; a cold start sets `Program.StartSystemRequested` and `MainForm` starts the system right away. `--start --start-only` sends the signal only and exits without launching a second copy.
legacy: `Ets2Telemetry.exe` is disabled; `ets2-telemetry-server.dll` is not required by the current startup path.

## Track save contract
request: client sends `{format:"compact_v2", data, meta, mapData, customTargets, requestId}` to 8084.
commands: `save_trail`, `start_recording`, `stop_recording`, `reset_recording_origin`, `add_random_target`, `remove_random_target`, `reset_target_reached`, `set_overlay_category`, `set_overlay_hidden`, `set_quest_collapsed`, `set_quest_tab_state`, `show_game_ui`, `hide_game_ui`, `minimap_show`, `minimap_hide`, `minimap_auto`, `ar_layer_visible`, `play_sound`.
guards: save only after actual ETS2 pause confirmation; duplicate `requestId` must not create a second track.
response: `{status:"ok"|"error", message, requestId}`.
compact: first line metadata JSON; trail `<t>;<x>;<z>;<heading>;<speed>`; data `D;...;<headOffset>`; events `E;...`.
headOffset: six numbers; index 3 is normalized heading 0..1.

ar1_fov: `ArBridge.FovDegreesAr1` = **105** + `AppSettings.Ar1FovDeg` (default 105); hotkeys Ctrl+PGUP/PGDN ±1° → command `ar_fov` → `CFG.fovDeg` (AR1), `state.fovDeg` (minimap), `MapEditor2SetFov` (editor 2). tuned_defaults_v1.0.40.39: USER-TUNED VALUES ARE THE DEFAULTS — horizontal FOV AR1 **105°**, vertical FOV AR1 **65°**, camera roll mode **2 (+roll)**, camera roll fraction **0.5**. hotkey_alt_forbidden: NEVER register Alt-containing hotkeys (Windows grabs them: system menu / Alt+Tab; `RegisterHotKey` fails with 1409). ar1_process: external `WebOverlay` window (`MainWindowTitle` contains "AR HUD"); AR1 button state is derived by scanning processes (2 s tick), not by a flag.
ar_feed: C# `MainForm.ArTarget.cs` is the only producer; events `ar_target`/`ar_telemetry`/`ar_pin`/`ar_fov`/`debug_show` over 8084. `StartArTargetFeed` forces `_arTruckChanged=true`, `_arTelemetryForced=true`, `_arCitiesSent=false`, `_arLastHeadSent=null`; each new WS client triggers `ForceArDataResend(reason)`.
ar_feed_rule: `_arTelemetryForced` is a STICKY request flag — incoming data must NOT clear it; only the tick clears it after a successful send. `_arTruckChanged` alone is overwritten by `ApplyPlacementJson` (WS + 1 Hz REST) before the 33 ms tick (root cause of "AR1 shows no telemetry").
ar_tick: `System.Threading.Timer` (NOT `System.Windows.Forms.Timer` — the WinForms timer did not tick at all, so NO data ever reached AR1). `StartArTickTimer`/`StopArTickTimer`/`QueueArUpdateTick`; WS/UI work marshalled with `BeginInvoke`; `Interlocked _arTickBusy` prevents overlapping 16 ms ticks. Liveness line `[AR] tick alive:` in app_data every 5 s.
ui_thread_rule: ⛔ NEVER DO HEAVY I/O ON THE UI THREAD IN THE AR TICK. `ArUpdateTick` runs via `BeginInvoke` (UI thread). Reading/parsing ~1.9 MB of JSON there (cities + Overlays + 80 SDO files, measured SDO ~960 ms) stalled the tick: measured `tick alive` intervals went 5010 ms -> **5903 / 6483 / 6558 ms**. The point model is now built in the BACKGROUND (`QueueArModelRebuild` + `Task.Run`, pure `BuildArModel`), the `_arPoints` reference is swapped atomically under `lock`, and all consumers read it via `ArPointsSnapshot()`. Rebuild interval 5 s -> 15 s (`ModelRefreshIntervalMs`), because the model is static. ALSO: `SdoLoader.LoadAll()` is CACHED by a directory fingerprint (newest write time + file count); `InvalidateCache()` after a new editor export.
process_enum_rule: ⛔ NEVER CALL `Process.GetProcessesByName` IN PER-FRAME CODE. `GetGameScreen()` (finds the screen of eurotrucks2/amtrucks2) was called from `BuildHeightsPayload`/`LogArTiltDiagnostics` up to 30 times per second — the second cause of the freeze. It is now cached for 2 s (`GameScreenCacheMs`); reset with `InvalidateGameScreenCache()`.
ar_point_color: POINT COLOR MUST BE PASSED FROM `PointData.Color` (same value as the minimap/sidebar), NOT an empty string. An empty string makes the page fall back to `KIND_FALLBACK.poi = '#70d1fe'` (blue) — that was "all points are always blue". The colour source is `SdoMeta.ColorHexOf` (company `#a080e0`, garage `#9aa8b8`, fuel_l `#ffa040`…), so without the SDO layer there is no colour at all. The point model is now ~5748 entries (was 1200) — every heavy pass over it must stay off the UI thread.
publish_cache: `compile.ps1` clears WebView2 profiles RECURSIVELY (the WebOverlay profile lives at `publish\data\bin\WebOverlay.exe.WebView2\EBWebView`, two levels down, ~34 MB) and verifies delivery (`data\` vs `publish\data`: MD5 for web content, sizes for the rest) plus that no `*.WebView2`/`EBWebView` folders remain. Overlay host is killed before wiping (it holds profile locks). Stage 3d then cleans `MemoryAI\LOGS` (ALL files and subfolders except `README.md` — temporary diagnostic logs must not survive a successful build). ⛔ DESTRUCTIVE POST-PROCESSING ONLY AFTER CONFIRMED SUCCESS: `dotnet publish` is checked via `$LASTEXITCODE` (aborts cleanup on failure) and the `$deliveryOk` flag gates the LOGS wipe — a failed build must not destroy the very logs needed to diagnose it.
overlays: `StartWebOverlay` launches `WebOverlay.exe` (SEPARATE REPOSITORY `F:\repo\weboverlay`: `Program.cs`, `HelpPage.cs`, `LocaleData.cs`) with `web_ui_hybrid.html` + `append web_pda_map.html` + `append web_pause_logo.html` + `append web_quests.html` + `append web_notifications.html` (+ `append web_heights.html` only when `ShowHeightsWindow`); the AR HUD layer is appended by `StartArOverlayLayer()`. Geometry comes from `ComputeOverlayGeometry` (kind by URL substring: map / hybrid / heights / logo / fullscreen for ar_hud+quests+notifications) into the SINGLE file `%APPDATA%\WebOverlay\config\<safe-url>.txt` (X, Y, zoom, W, H). NEVER re-introduce PER-MONITOR state files (`<url>__monitor_DISPLAY<n>.txt`) — they made every monitor own its geometry, so switching looked like "all settings reset" and left orphans; the overlay moves between monitors by COORDINATES. Fullscreen layers (ar_hud / quests / notifications) are REWRITTEN whenever the game screen bounds change, which is why the quest hotspot may assume client coords starting at 0,0.
weboverlay_controls: the "move to next monitor" hotkey was REPLACED by a STEP TOGGLE (`AppConfig.ToggleStep`, default `Ctrl+Shift+Alt+Oem5`): normal step <-> x3 (`StepMultiplier`) for move/size/zoom. The toggle is the ONLY action executed on key RELEASE (arm on press -> execute on release); everything else is continuous. Move/size/zoom MUST be applied in the tick (`ApplyHeldManipulation`, ~15 ms) via GLOBAL key state (`GetAsyncKeyState` + `IsBindingHeld`) — handling them in `OnKeyDown`/`CheckBinding` made them fire once and then "require re-selecting the window with the yellow frame" (the window lost focus after the first action, so KeyDown stopped arriving). WebOverlay must be rebuilt in its own repo and its exe copied to `f:\repo\ets2_assist\data\bin\WebOverlay.exe` (+ publish) before running `compile.ps1`.
weboverlay_defaults: if no config exists (`ApplyDefaultState(PrimaryScreen)`, URL-based, clamped into the working area): `web_pda_map` -> BOTTOM-LEFT (side = 30% of working height); `web_ui_hybrid` -> bottom-CENTRE (42% x 32%); `web_heights` -> TOP-RIGHT (34% x 30%); `help.html` -> 800x1000 at left+560 / top+15; otherwise (pause-logo) -> TOP-LEFT (side = 18%).

## Overlay visibility policy (single authority)
overlay_policy: THERE ARE EXACTLY **TWO MUTUALLY EXCLUSIVE UI CATEGORIES** and never more than one on screen. Authority = C# `UI/WebUIManager.cs`; pages are PASSIVE and only apply the pushed result through the shared `data/js/ui_category.js` (CSS on `html.ets2-cat-game` / `html.ets2-cat-interactive` over `data-category="game|interactive"`). Command: `set_overlay_category {category}` over 8084.
overlay_categories: **interactive** (pause UIs) = mini-logo (`web_pause_logo.html`) + the quest window and its «Квесты» tab (`web_quests.html`). **game** (game-camera UIs) = hybrid (`web_ui_hybrid.html`), minimap (`web_pda_map.html`), notifications (`web_notifications.html`), AR HUD (`web_ar_hud.html`).
overlay_policy_rules: game paused -> interactive ONLY (mini-logo always, plus the «Квесты» tab; NO minimap/hybrid). Game unpaused -> game ONLY (hybrid, minimap, notifications, AR; NO mini-logo/interactives). Additionally ALL overlays hide when the foreground window belongs to a THIRD PARTY (anything that is not the game and not our own `WebOverlay` process) — overlaying a user window is forbidden. Focus onto our own overlay changes nothing.
overlay_focus_hide: the third-party-focus rule hides the overlays TWICE: content via `set_overlay_hidden {hidden}` (8084, `data/js/ui_category.js` -> CSS class `ets2-hide-all` on `<html>`, which hides every `[data-category]` node even under `data-debug-show="1"`, plus `pointer-events:none` on the root) AND the real host windows via the named pipe `WebOverlayPipe` (`hide_all`/`show_all`, handled in `WindowManager.SetAllLayersHidden`). The pipe is the ONLY correct channel (connect timeout 400 ms, failure is ignored): launching `WebOverlay.exe hide_all` would create a NEW host instance showing the help page when no host is running. `WebUIManager.SendOverlayHostCommand` always sends the CURRENT `_overlayLayersHidden` under a lock, so racing ticks cannot invert the state. The host is idempotent (`_layersHidden`), hides via `OverlayForm.SetLayerHidden` (window + `_backgroundForm`, `_layerHidden` also gates `SetContentVisible`) and applies the state to later-created windows.
weboverlay_pipe: named pipe `WebOverlayPipe` (single line, `|`-separated): `append|url`, `close|url`, `hide_all`, `show_all`. The server accepts 1-token commands (`parts.Length < 1` guard), so any new single-token command works without touching the client. Unknown tokens are ignored.
overlay_hysteresis: `CheckPauseAndUpdateUI` runs every 500 ms; the game-visible decision needs **2 stable ticks (~1 s)** before it is committed, so a momentary focus loss does not make the overlays flicker.

overlay_timer: ⛔ **THE POLICY MUST NOT RUN ON `System.Windows.Forms.Timer`** — it did not tick at all while the game held the window (session 13:34: NO policy line for 22 minutes; the map/hybrid/quests then "lived their own life": minimap stayed in pause, no hybrid, no quest dialog). It is now `System.Threading.Timer` (`StartPauseCheck` / `QueuePauseCheck` / `Interlocked _pauseCheckBusy`, flag released in `finally`), exactly as the AR tick and MapEditor2 already do. The HTTP pause probe runs **in the pool thread**; only the decision is marshalled with `BeginInvoke`. Liveness line `[UI] политика жива: …` in app_data every 30 s — without it, silence is indistinguishable from "nothing to show".

focus_steal: ⛔ `MoveToMonitor` takes focus ONLY on an explicit tray action (`activate: true`). The automatic startup move passes `activate: false`: the game is already running, and grabbing focus pulled it out of ETS2 (telemetry went to "placement нет (пауза/окно игры неактивно)" and the policy saw "фокус вне игры", hiding everything).
overlay_startup: ALL overlay windows are started together by `StartWebOverlay` (hybrid, minimap, mini-logo, quests, notifications) plus `StartArOverlayLayer()`; the AR button only toggles the layer (`ar_layer_visible`), it never creates/destroys the window, so the set of WebOverlay windows is constant and the category policy always covers every layer.
overlay_no_loading_screen: the quest loading screen is REMOVED (`loadingScreen.enabled=false`); a future version must not reintroduce a screen between pause and the quest window.
weboverlay_noactivate: the overlay host windows are created with `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` and `ShowWithoutActivation=true`, and `OnActivated` is suppressed (`Program.SuppressOverlayActivation`) — the host NEVER steals focus from the game, and the game keeps its foreground window while the overlay owns the mouse.
weboverlay_colorkey: the lime colour key is a property of `WS_EX_LAYERED`, so `WS_EX_LAYERED` MUST stay set in BOTH clickable and click-through states; only `WS_EX_TRANSPARENT` switches. `OverlayForm.ApplyClickThroughStyle` is the single owner of that style transition (it returns whether anything actually changed, and only a real change may be logged). `OverlayTransparencyFix` only repairs drift: it READS BACK the key with `GetLayeredWindowAttributes` and writes `SetLayeredWindowAttributes` only when the key is really missing, and it calls `Invalidate()` only on a real state change. ⛔ Never repaint a layered window on a timer (remove/add from the compositor = visible blink) and ⛔ never include `bAlpha` in the drift check — WebView2 resets it to 0 while `LWA_COLORKEY` stays correct.
weboverlay_clickability: `set_clickable {value}` only works for `web_quests.html`, `web_notifications.html`, `web_ar_hud.html`; every other overlay is permanently click-through.
weboverlay_hotspot: a COLLAPSED quest window is not clickable as a whole — `set_clickable_hotspot {xr,yr,wr,hr}` (FRACTIONS of the client area; the host converts them with `ClientSize` in `SetClickableHotspotRelative`) declares the only region that accepts the mouse. ⛔ Fractions, not CSS pixels: the host declares NO DPI manifest, so page pixels diverge from client pixels under display scaling. Absolute `{x,y,w,h}` is still accepted as a fallback. `WM_NCHITTEST -> HTTRANSPARENT` alone does NOT work (WebView2's child HWND hit-tests first), so the host switches `WS_EX_TRANSPARENT` from a 30 ms timer based on `Cursor.Position` vs the hotspot rect (`UpdateHotspotCursorState`). Empty rect + `_clickable=false` = whole window click-through. ⛔ The 30 ms timer runs ONLY while a hotspot is set (`UpdateHotspotTimerState`): with an empty rect it used to re-run the hit test every tick and each style write rebuilt the layered window → the overlay appeared to blink.
weboverlay_return_focus: `return_focus` (sent by the quest page when it collapses) hands the foreground back to the game (`ReturnFocusToGameIfPossible`).

## Quest interactive window
quest_toggle_tab: ⛔ TAB IS AN APPLICATION HOTKEY, NOT A PAGE keydown. The overlay host is deliberately `WS_EX_NOACTIVATE` + `OnActivated`-suppressed (a real focus grab steals the foreground from ETS2 and breaks telemetry — the v1.0.40.54 regression), so the quest page never receives WM_KEYDOWN. Tab is therefore registered by `MainForm` (`HOTKEY_QUEST_TOGGLE = 9022`, `MOD_NOREPEAT` only, no Ctrl/Shift) and forwarded as `quest_toggle_collapse`, which the page routes through the SAME `collapseWindow`/`expandWindow` used by the ← button (so the 250 ms `blockToggle()` guard and the `quest_window_state` report both still apply). ⛔ THE HOTKEY IS REGISTERED/UNREGISTERED DYNAMICALLY by `SetQuestToggleHotkeyActive(bool)` from `WebUIManager.ApplyOverlayVisibility`: active ONLY while `showInteractive` is on screen (the «Квесты» tab or the window), and released in `StopSystem`. A permanently held TAB would be swallowed system-wide.
quest_cursor: while the window is expanded the layer shows the normal arrow cursor (`#questApp.paused{cursor:default}` + `applyCursorLayer()` in `quests_ui.js` called from `syncInput`) — every other overlay keeps the hidden game cursor. Collapsing hands the cursor back to the game (`return_focus`, unchanged).
quest_window_state: the app REMEMBERS collapsed/expanded across RESTARTS (`AppSettings.QuestWindowCollapsed` + `_questCollapsed` in `WebUIManager`, seeded by `LoadQuestWindowState()` at system start) and restores it on every pause (`set_quest_collapsed`); pausing NEVER auto-opens the window any more. The page reports changes back with `quest_window_state {collapsed}` over 8085 ONLY for player actions (`applyCollapsed(value, notify, report)` — a report on page load would overwrite the saved view), which calls `OnQuestWindowCollapsedChanged` -> `AppSettings.Save()`. ⛔ ONE GESTURE = ONE TOGGLE: a gesture that delivered two click events (double click on ←, or bubbling to `#questApp`) used to send «свёрнуто» and «развёрнуто» 1 ms apart, so the window never visually collapsed — `collapseWindow`/`expandWindow` now go through `blockToggle()` (250 ms guard, `lastToggleAt` in `data/js/quests_ui.js`).
quest_tab_hotspot: the collapsed tab is the ONLY clickable thing while paused+collapsed; its native hotspot is sent as FRACTIONS of the client area (`set_clickable_hotspot {xr,yr,wr,hr}` -> `SetClickableHotspotRelative`) because the host has no DPI manifest, and it is re-sent on `transitionend` of the 220 ms slide-in (mid-animation the bounding rect is still offset).
quest_tab_pulse: «Квесты» pulses (2 s, smooth yellow) whenever an interactive is in range — `QuestRuntime` pushes `_host.SetQuestInteractiveSignal(hasInteractive)` (tick) -> `set_quest_tab_state {hasInteractive}`. No interactives -> the tab is static by design.
quest_radius_notification: the "quest in range" notification carries `durationMs = QuestRuntime.RadiusNotificationMs` = **12000**; `web_notifications.html` uses `Math.max(1500, Number(n.durationMs) || 4500)`, so every other notification keeps the 4.5 s default.
quest_dialogue_flow: opening the window ALWAYS starts from the initial state (no retained dialogue): `_activeDialogue` is not pre-seeded, `SelectInteraction` clears the retained key and starts from `ResolveEntryDialogue`, and a newly connected page receives no `dialogue` field. The LAST option of every dialogue is the exit (`"close": true`), which nulls the selection and resets the centre panel.
quest_dialogue_effect: the NPC line changes smoothly — the old text fades over 150 ms, then the new one is typed character by character (`renderDialogue` + `typeInto`, ~55 chars budget, 16 ms step) in `data/js/quests_ui.js`.
quest_text_convention: ROLE-PLAY text = Roboto, pure white with black outline/shadow, no brackets. SERVICE text = Courier, `rgba(255,255,255,.8)`, passed as a separate `serviceText` field (no brackets in the data; the UI adds them). SKILL/STAT REQUIREMENTS = Courier, colour **#0048ff**, bracketed `[Сила 3]`, name + numeric level (`DescribeRequirements` emits them; no quest uses requirements yet). Rewards/carried items are service text too.
quest_layout: `web_quests.html` header is TWO COLUMNS — 25 % SQUARE image (no transparency) on the left, 75 % NPC text on the right; the answers block is BELOW; answers highlight on hover. The collapse button (←) sits in the top-right of the window; the collapsed window slides left off-screen (`translateX(calc(-100% - 40px))`) and only the left-edge tab stays clickable. Clicking the transparent background of the quest window also collapses it (only when the click target is literally `#questApp`). Empty state (nothing selected) shows `EmptyHint` in the centre.
quest_marker_height: `data/js/ar_quests.js` adds the CAMERA EYE HEIGHT to quest AR markers so they sit at player eye level instead of lying on the ground: `eyeHeightAboveGroundAt(camPos)` derives the ground Y from the camera-side `groundPlane` plane. ⛔ In the `ar_telemetry` payload `groundPlane` is a SIBLING of `camera`, NOT a child — reading `camera.groundPlane` silently yields 0 (that was the "markers on the ground" bug).

quest_icons: quest markers are drawn from RASTER icons `data/quests/images/Pointer_*.png` (32x32, verified by silhouette + colour analysis). ⛔ NAMING IS NOT OBVIOUS (do NOT guess it — proven by silhouette 10x28 vs 15x26 + colour): `Pointer_quest_on/off` = «!» (yellow_exclamation); `Pointer_questdone_on/off` = «?» (yellow_question); `*_on` = yellow/active, `*_off` = gray/inactive, therefore `gray_question` ALWAYS uses the `_off` file and `yellow_question` the `_on` file. Consumers and sizes: AR (`js/ar_quests.js`) draws at the SAME size ramp as before via `markerStyle(dist).size`, where `size` 10 -> 32 px (1:1, "32x32 unchanged") down to ~9.6 px at 500 m+, and the offscreen edge pointer uses 26 px; minimap (`js/map_draw.js`) draws quest POIs at a scaled **12x12** (`questPointerIconSizePx`, source 32x32; was 8 — unreadable at that size) — the URL arrives in the POI field `__questIcon` set by `js/quests_client.js`, and it takes priority over the SDO category icon; quest window list 28 px (`js/quests_ui.js`); editor 2 sidebar 16 px (`js/quest_editor.js`). ⛔ EVERY renderer keeps a FALLBACK: the old SVG / text glyph is drawn when the bitmap is not yet decoded (`img.complete && img.naturalWidth>0`), otherwise the marker disappears on the first frames. ⛔ `js/quest_editor.js` runs INSIDE `data/map_editor2/index.html`, so its asset paths must be `../quests/images/...` (injected with `src='../js/quest_editor.js'`) — a root-relative path 404s there.

quest_marker_smooth: quest AR markers use the SAME smoothing as AR1 points (target extrapolation + `k = 1 − exp(−dt/tau)`), otherwise they jitter on the frames between telemetry packets. `ar_hud.js` publishes `window.__arSmooth = { cfg: SMOOTH, view: camSmoothView }` — `ar_quests.js` reads `cfg` for the SHARED tau and prefers `view` (the already smoothed pose) so both AR layers look from one point. ⛔ The handle is published AFTER `SMOOTH`/`camSmoothView` are declared (`const` TDZ — publishing next to `ar` would throw `ReferenceError`). Velocity is estimated in the PACKET handler, never in the frame. Default tau = **80 ms** (`Ar1SmoothTau`).

quest_ar_camera_pos: ⛔ `window.__arSmooth.view` (the shared smoothed pose published by `ar_hud.js`) exposes `camX`/`camY`/`camZ`, while `ar_quests.js`'s OWN smoothed struct uses `x`/`y`/`z`. Reading only `camPos.x` yielded `undefined` -> NaN -> `sp.x > -90` false -> **the quest icon was silently never drawn (only the AR crosshair stayed visible)**. ## Rules
version: `MAJOR.MINOR.PATCH-DESCRIPTION-YYYY.MM.DD-HHmm`; every functional change increments PATCH; synchronize BuildInfo.cs, project VersionPrefix, web badges, `data/web_runtime_manifest.json`, `data/ets2_assist_build.txt`, and playback build log.
source_of_truth: edit root `data/`; publish is generated output; do not use publish as the only source.
release: `dotnet publish -c Release`; verify EXE and `publish/data` after publishing.
cache: preserve stable overlay URLs; invalidate changed local assets through existing cache/version mechanism.
compatibility: preserve ports, REST paths, WebSocket commands and compact track format unless plan explicitly changes a contract.
logging: use existing Logger/AppendLog; log requestId and data-flow failures; do not silently hide new errors.

log_split_rule: ⛔ TWO SINKS, STRICTLY SEPARATED. `Logger.Workflow` / `Logger.Info` = `app_workflow.log` (**stages and state transitions**); `Logger.Data` = `app_data.log` (**values/data**). CRITICAL: `AppendLog` writes to the workflow file AND to the log console, while `AppendDataLog` / `Logger.Data` go to the app_data file ONLY — this is exactly why per-frame diagnostics must use `Logger.Data`. `SendCommandToMap` already follows this (`IsStreamingCommand`: streaming commands -> `Logger.Data` only). Fixed in v1.0.40.55: `[AR] TILT` / `[AR] HORIZON-GEOM` (were `AppendLog`, 2592 lines in the workflow log) and the obsolete "Hotkeys: …" register summary and "Language saved to config.json" now use `Logger.Data`. `Logger.OnLogMessage` is wired to the console with `persistWorkflow: false`, so the console shows exactly the workflow stream.
logger_init: `EnsureLogger()` is idempotent and runs BEFORE `InitializeLanguage()` — the logger used to be created in `InitializeProcessManager`, which runs later, so any data-logged line from language init was silently dropped (`Logger.Current` was null).
window: save/restore bounds with `Screen.DeviceName`; clamp to current working area if monitor is absent.
startup_monitor: the main form must NOT open on the monitor where the game runs (`ApplyStartupMonitorPreference` in the `Shown` handler). `FindGameScreenNow()` re-scans `eurotrucks2`/`amtrucks2` main windows instead of `GetGameScreen()` (whose 30 s cache may still hold another monitor); if the saved monitor or (when nothing is saved) the monitor the form actually landed on is the game monitor, the form is moved once to the NEXT available monitor via the shared `MoveToMonitor` path. With one monitor, or no game running, nothing changes. `MoveToMonitor` normalizes the window first (`FormWindowState.Normal`), moves it, and maximizes again — a maximized form ignores `SetDesktopLocation`.
tray_show_menu: the tray menu has a disabled header «Показать:» followed by one `Монитор N` item per `Screen.AllScreens` (named fields `trayShowHeader`/`trayMonitorItems`, rebuilt on `trayMenu.Opening`). Choosing a monitor ONCE moves the main form (`MoveToMonitor`: clamp size to the working area, normalize → `SetDesktopLocation` → maximize, `Show`, `ForceForegroundWindow`) and persists the bounds — needed because the app can end up under the game with the game holding the focus. Labels come from named `ToolStripMenuItem` fields, never from indices.
